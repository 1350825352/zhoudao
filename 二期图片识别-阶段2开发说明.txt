一、需求概述
--------------------------------------------------------------------------------
在一期代码基础上进行改造, 在 admin-v3 左侧菜单栏新增"换数据源"目录,
集中管理以下三个开关/切换:

1. 视频流任务开关: 开启/关闭知眸视频流自动创建任务
2. 图片识别任务开关: 开启/关闭图片识别流程
3. 警情数据源切换: 切换警情信息显示的数据源(视频识别/图片识别已清洗)

开发过程中新增的优化(方案外):
4. 知眸(GPU)与自有模型(CPU)由串行触发改为并行触发
5. 自有模型加 0.5 秒上传间隔
6. screen-v3 警情图片预览框样式优化(解决留黑边)


二、关键决策确认
--------------------------------------------------------------------------------
决策1: 视频任务开关关闭时
  用户选择: 方案B - 立即关闭所有运行中的视频任务
  (不等自然结束, 立即遍历 zhimou_status=1 的 live_stream 调用 closeZhimouTaskByLiveStreamId)

决策2: 图片识别数据源显示
  用户选择: 只显示 clean_status != 0 的已清洗数据
  (避免脏数据展示给前端)

决策3: 警情数据源切换范围
  用户选择: 全局切换
  (目前只有一个机场, admin 设置后所有用户看到同样的数据源)

决策4: 图片识别任务开关
  用户选择: 当前控制测试入口, MinIO 接入后控制事件接收接口

决策5: 切换按钮位置
  用户选择: 只在 admin-v3 左侧"换数据源"菜单
  (screen-v3 无需切换按钮, 自动读取全局设置)

决策6: 知眸与自有模型触发方式(开发中新增)
  用户选择: 并行触发
  (知眸用 GPU 在远端服务器, 自有模型用 CPU 在本地/另一台机器, 硬件不冲突
   两者无数据依赖, 仅最后的数据清洗需要两边结果都到齐, 故可同时开跑)

  逻辑:
    @Scheduled(fixedDelay = 1000L)
    public void autoCheckLiveStreams() {
        // 检查视频任务开关
        if (!taskSwitchService.isVideoTaskEnabled()) {
            // 开关关闭: 立即关闭所有运行中的知眸视频任务
            List<LiveStream> runningStreams = liveStreamMapper.selectList(
                new LambdaQueryWrapper<LiveStream>()
                    .eq(LiveStream::getZhimouStatus, 1)
                    .eq(LiveStream::getDeleted, 0));
            for (LiveStream live : runningStreams) {
                closeZhimouTaskByLiveStreamId(live.getId());
            }
            return; // 不再创建新任务
        }
        // 原有逻辑...
    }

  关键行为:
    - 关闭开关: 立即关闭所有 zhimou_status=1 的视频任务 + 停止自动创建
    - 开启开关: 恢复自动调度

4.5 知眸/自有模型并行触发改造(开发中新增, 核心优化)
  ----------------------------
  修改文件: ImageRecognitionTestController.java (POST /run 接口)

  改造前: 串行触发 - 先跑知眸全部上报完, 再跑自有模型, 白白等待
  改造后: 并行触发 - 知眸与自有模型各自独立线程同时开跑

  理由:
    - 知眸用 GPU(远端服务器), 自有模型用 CPU(本地或另一台机器)
    - 硬件互不冲突, 无数据依赖
    - 仅最后的数据清洗需要两边结果都到齐(由前端收到知眸回调后再触发 /cleanup)

  实现要点:
    - 知眸线程 zhimou-image-batch: 调 createAndReportImageBatch 批量上报
    - 自有模型线程 self-model-detect: 循环调 detectAndSave, 每张间隔 0.5 秒
    - 主线程 join() 等两个子线程"上报/识别动作"完成(不等知眸回调)
    - 用 final 数组承接子线程结果, 主线程返回时读取

  自有模型 0.5 秒间隔:
    for (File imgFile : imageFiles) {
        selfModelDetectService.detectAndSave(imgFile, threshold, imageBaseDir);
        Thread.sleep(500); // 0.5 秒, 降低 CPU 瞬时占用
    }

  并行验证日志(关键节点带时间戳 HH:mm:ss.SSS):
    - [并行-知眸] >>> 主线程准备启动知眸线程
    - [并行-知眸] === 知眸线程开始执行
    - [并行-自有] === 自有模型线程开始执行
    - [并行-自有] --- 处理第 N/16 张 file=xxx
    - [并行-知眸] === 知眸线程结束(批量上报完成)
    - [并行-自有] === 自有模型线程结束 success=X, fail=Y
    - [并行-主] 两个子线程均结束, 汇总结果
  判断标准: 两线程"=== 开始执行"时间戳相差几毫秒, 日志交错出现

八、交互流程
--------------------------------------------------------------------------------
8.1 视频任务开关流程

  admin "换数据源" → 点击"视频流任务开关: 关闭"
    ↓
  PUT /api/task-switch/video_task?value=0
    ↓
  后端: 更新数据库 + 更新 Redis(switch:video_task=0)
    ↓
  下一秒调度时:
    autoCheckLiveStreams() 读 Redis → video_task=0
    ↓
    立即关闭所有 zhimou_status=1 的视频任务
    后续不再创建新任务

8.2 警情数据源切换流程

  admin "换数据源" → 切换警情数据源为"图片识别"
    ↓
  PUT /api/task-switch/alert_data_source?value=image
    ↓
  后端: 更新数据库 + 更新 Redis(switch:alert_data_source=image)
    ↓
  screen-v3 警情页面轮询 /alerts:
    后端读 Redis → alert_data_source=image
    ↓
    查 zhimou_image_detection WHERE clean_status != 0
    ↓
    返回图片识别结果(已清洗)

8.3 图片识别并行触发流程(新增)

  POST /api/test/image-recognition/run (image_task 开关需=1)
    ↓
  扫描 testimage 目录 16 张图
    ↓
  同时启动两个线程:
    ├─ zhimou-image-batch 线程: 批量上报知眸(每张1秒间隔, 知眸限制)
    └─ self-model-detect 线程:  同步识别(每张0.5秒间隔)
    ↓
  主线程 join 等两个子线程上报/识别完成(不等知眸回调)
    ↓
  返回 {zhimouTaskId, selfModelSuccess, selfModelFail, cleanupHint}
    ↓
  知眸异步回调陆续到达 → 入库 zhimou_image_detection
    ↓
  前端收到回调到齐后调用 /cleanup-all 触发清洗

十一、开发中的坑与注意事项
--------------------------------------------------------------------------------
坑1: admin-v3 请求 URL 重复加 /api 前缀 → 404
  .env 设 VITE_API_BASE_URL='/api', axios 自动加前缀
  页面代码再写 '/api/task-switch' → 实际请求 /api/api/task-switch → 404
  修复: 页面写 '/task-switch', 不带 /api

坑2: 知眸图片保存目录权限异常 → AccessDeniedException
  原配置指向旧项目目录 H:/traeproject/ceshisikongapiAI/zhimou-images
  修复: 改为 H:/traeproject/zhoudao/zhimou-images 并创建目录
  配置文件: application-company-a.yml 的 zhimou.openapi.save-root-dir

坑3: cmd 下 curl 传 JSON body 失败 → 400 Bad Request
  cmd 不认单引号字符串, -d '{\"key\":\"val\"}' 传给后端的 body 损坏
  修复: JSON 写到文件, 用 -d @文件 (test-req.json)
  或改用 PowerShell, 单引号写法 -d '{\"key\":\"val\"}'

坑4: "知眸回调 28秒/张, 8分钟到齐" 的估算严重高估
  来源: 设计文档风险章节的拍脑袋估算值, 无实测依据
  实测: 知眸 GPU 推理几乎实时, 每张回调延迟约 0.6-1 秒
        16 张全部到齐约 17 秒, 远非 8 分钟
  修复: 已从代码 cleanupHint 文案中去掉 "28秒/张" 误导性数字
