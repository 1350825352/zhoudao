阶段3: MinIO 轮询图片同步方案 - 开发总结
================================================================================
生成时间: 2026-08-27

================================================================================
一、功能概述
================================================================================

实现无人机飞行任务图片的自动化处理流程：
1. 通过 MinIO 轮询发现新的飞行任务批次
2. 下载图片到本地临时目录
3. 并行调用知眸 GPU 和自有模型 CPU 进行识别
4. 结果自动入库和清洗
5. 批次完成后自动清理临时目录

================================================================================
二、核心流程
================================================================================

MinIO 轮询 (每30秒)
    │
    ├─ 扫描 fh_sync/{ORG}/{PROJ}/media/{TASK_UUID}/ 前缀
    │
    ├─ 批次状态检查 (Redis):
    │   ├─ COMPLETED → 永久跳过
    │   ├─ PROCESSING (TTL=30min) → 暂时跳过
    │   └─ 无状态 → 进入处理队列
    │
    ├─ 完整性校验 (双重校验):
    │   ├─ DJI API: uploaded_file_count >= expected_file_count
    │   └─ DJI media接口数量 == MinIO文件数
    │
    ├─ 获取分布式锁 (SETNX PROCESSING, TTL=30min)
    │
    ├─ 下载图片到 zhimpou-minio-temp/{taskUuid}/
    │
    ├─ 创建初始 Redis 追踪 key (防止竞态条件)
    │
    ├─ 并行分派处理:
    │   ├─ 知眸 GPU: createTask → reportImage × N → 回调写DB
    │   └─ 自有模型: loadModel → inference → 写DB
    │
    ├─ 自动清洗 (双路结果到齐后)
    │
    └─ 批次完成判断:
        ├─ Redis 追踪 key 全部删除
        ├─ DB 无待清洗记录
        └─ 标记 COMPLETED + 删除临时目录

四、Redis 状态管理
================================================================================

Key 格式                                    | 生命周期                              | 说明
------------------------------------------- | ------------------------------------- | ----------------------------
minio:flight:{taskUuid}                     | PROCESSING(30min) → COMPLETED(永久)   | 批次级状态
minio:flight:img:{taskUuid}/{file}          | pending → 处理完成后删除               | 图片级追踪
zhimou:img:meta:{taskId}:{frameId}          | 创建后删除                              | 知眸图片元数据映射

================================================================================
五、已修复的问题
================================================================================

1. 批次过早 COMPLETED 竞态条件
   - 问题: tryCompleteMinioBatch 检查 Redis keys 为空时，可能在图片还没开始处理时就标记批次完成
   - 修复: 下载完成后立即为每张图片创建初始 Redis key (status=pending)
   - 状态: 已修复 ✅

2. reportImage 返回 null 兜底方案
   - 问题: 知眸服务偶发返回 null，导致图片处理中断
   - 修复:
     * 增加 10 秒超时设置
     * 三步兜底逻辑: DB入库(clean_status=1) + Redis标记(zhimou=1,failed=1) + 触发检查
   - 状态: 已修复 ✅

================================================================================
六、待处理的问题
================================================================================

1. 文件完整性校验 (明天处理)
   - 问题: 如果 DJI 在最后一个文件完全上传前就更新 uploaded_file_count，可能导致下载不完整的图片
   - 现状: DJI API 不返回文件大小，MinIO 可能有上传中的文件
   - 建议方案:
     a. 方案A: 双次检查 - 检测到匹配后等待30秒，再检查文件大小稳定性
     b. 方案B: 下载后验证 - 下载后检查文件大小(>1KB)和可打开性(ImageIO.read)
     c. 方案C: 稳定等待 - 检测到匹配后等待60秒再处理
   - 状态: 待实现 ⏳

2. MQTT 触发优化 (可选)
   - 问题: 当前30秒轮询有延迟，图片上传完成后需要等待1-2轮轮询
   - 优化: 利用 MQTT 的 mode_code 变化（降落时）主动触发 MinIO 轮询
   - 优点: 延迟从30s降到<1s
   - 状态: 可选优化，待评估 ⏳

九、数据库表
================================================================================

1. zhimou_image_detection (知眸检测结果表)
   - local_image_name: 本地图片路径 ({taskUuid}/{fileName})
   - task_id: 知眸任务 ID
   - frame_id: 知眸帧 ID
   - hit_count: 检测到的目标数量
   - clean_status: 清洗状态 (0=未清洗, 1=已清洗)

2. self_model_image_detection (自有模型检测结果表)
   - local_image_name: 本地图片路径
   - call_status: 调用状态
   - hit_count: 检测到的目标数量
   - clean_status: 清洗状态

================================================================================
十、注意事项
================================================================================

1. 批次 Redis key 为永久状态，已完成批次不会重复处理
2. PROCESSING 状态 TTL 为 30 分钟，超时后可重新处理
3. 知眸并发限制为 2 个活跃任务，需主动调用 deleteTask 关闭
4. MinIO 临时目录会在批次完成后自动清理
5. 手动重试接口: POST /api/minio/retry?taskUuid=xxx
