0. 已验证关键数据结论（读前必读）
================================================================================

MinIO 完整 ObjectKey 样例：
  flydata/fh_sync/8566c7de-05ac-41ee-b260-1614848ed037
                  /826ccf49-8430-4037-a505-cd43b868d4d6
                  /media
                  /dbc84414-a612-4637-9964-ea4e8c3ca2a6
                  /DJI_20260826130711_0001_V.jpeg

实测对应关系：
  fh_sync/<ORG_UUID>/<PROJECT_UUID>/media/<TASK_UUID>/<filename>

  UUID1 (ORG)     = 8566c7de...  -> 配置 default-organization-uuid ✅
  UUID2 (PROJECT) = 826ccf49...  -> 配置 default-project-uuid      ✅
  TASK_UUID       = dbc84414...  -> /openapi/v2.0/flight-task/{TASK_UUID} 返回成功 ✅
  filename        = DJI_20260826130711_0001_V.jpeg -> media API 15 个 name 前缀一致 ✅

获取飞机 SN 的真实方式（已实测）：
  GET /openapi/v2.0/flight-task/detail
      ?workspace_id = 826ccf49... (PROJECT_UUID)
      &task_uuid    = dbc84414... (TASK_UUID)

  返回 flight_pieces[0].drone_sn          = 1581F8HHX25CL00A06BL ✅
       flight_pieces[0].drone_info.*      = 设备名/型号/SN ✅
       flight_pieces[0].task_name         = 任务名 ✅
       flight_pieces[0].take_off_airport_sn = 机场SN ✅
       flight_pieces[0].status            = success ✅

完整性校验（已实测）：
  GET /openapi/v2.0/flight-task/{TASK_UUID}
    返回 folder_info.expected_file_count = 15
          folder_info.uploaded_file_count = 15   ← 两者相等才说明公网->内网同步完毕 ✅
  GET /openapi/v2.0/flight-task/{TASK_UUID}/media
    返回 size=15，文件名全部为 DJI_*_V.*，与 MinIO ObjectKey 末尾段文件名前缀 100% 匹配 ✅

     健康检查：MinIO.bucketExists(bucket) 失败则 ERROR 日志。

  C. service/MinioPollingService.java          ← 【阶段3核心文件】
     @Slf4j @Service
     依赖注入：
       StringRedisTemplate                  用于批次 / 图片级状态
       MinioClient + MinioProperties        扫描 & 下载
       DjiOpenApiClient + DjiOpenApiProperties  拿 drone_sn & 完整性校验
       TaskSwitchService                    isImageTaskEnabled()
       ZhimouProperties                     appId/pkgId/imageBaseDir
       ImageRecognitionFacade（新抽）       processImageBatch()
       ImageCleanupService                  cleanupAllPending（兜底用）
     方法：
       - @Scheduled(fixedDelayString = "${minio.poll-interval-ms:30000}")
         scanAndProcess()
       - parseTaskUuidsFromMinIO() : List<TaskGroup>
         内部正则 ^fh_sync/(ORG_UUID)/(PROJECT_UUID)/media/([^/]+)/ 分组
       - boolean tryAcquireBatchLock(taskUuid) : SET minio:flight:{tuuid} PROCESSING
         带 TTL 30min，NX (只在不存在时设置)
       - void releaseBatchLock(taskUuid)    : 删除 PROCESSING 锁（仍在同步时用）
       - void markBatchComplete(taskUuid)   : SET minio:flight:{tuuid} COMPLETED 永久
       - void downloadBatch(taskUuid, localDir) : List<File>
         MinIO listObjects(prefix = fh_sync/..{PROJECT_UUID}/media/{taskUuid}/)
         只收 jpg/jpeg/png，getObject -> save(tempDir/{taskUuid}/filename)
       - void processSingleBatch(taskUuid, List<File> images, String droneSn)
         调用 ImageRecognitionFacade.processImageBatch(..., customLocalImagePrefix=taskUuid)
       - void cleanupTempFiles(taskUuid)     : 递归删除 tempDir/{taskUuid}
       - void sweepStaleBatches()            : （可选，每分钟）PROCESSING 超过2小时告警
       - retryBatch(taskUuid)                : （配合可选 MinioController.retry）
         DEL minio:flight:{taskUuid} 然后重新入队 processSingleBatch

  D. service/ImageRecognitionFacade.java   ← 【抽自 ImageRecognitionTestController】
     @Service
     依赖注入：ZhimouTaskService, SelfModelDetectService, TaskSwitchService
     方法：
       - BatchProcessResult processImageBatch(
             List<File> imageFiles,
             String aircraftSn,               // 阶段3从 detail API拿；阶段2从请求传入
             String appId,
             String applicationPackageId,
             BigDecimal threshold,
             String imageBaseDir,
             String customLocalImagePrefix,   // 阶段2=null沿用旧名去扩展名; 阶段3=taskUuid

4.7 批次状态（Redis）与图片状态（Redis）的衔接点
----------------------------------------------------------------------

  两类 Key 语义不同，不可混用：

  【批次级】minio:flight:{TASK_UUID}
    生命周期：PROCESSING (TTL 30min) → COMPLETED (永久)
    写入点：
      PROCESSING  → MinioPollingService.tryAcquireBatchLock (SET NX EX)
      PROCESSING  → MinioPollingService.releaseBatchLock (DEL, 仍在同步时)
      COMPLETED   → 两个入库点发现"该 taskUuid 下所有图片级 key 都已清理"
                   (tryMarkBatchCompleteByTaskUuid)
    读取点：
      MinioPollingService 每轮扫描 -> 若 PROCESSING 或 COMPLETED 跳过

  【图片级】minio:flight:img:{TASK_UUID/baseName}  HASH
    字段：zhimou=1 / self=1
    TTL：7 天
    写入点：
      zhimou=1 → ZhimouTaskServiceImpl.handleImageCallback
      self=1   → SelfModelDetectService.detectAndSave
    读取点：
      每次写入后立即 entries() 检查两个字段是否同时存在
      是 → cleanupSingleImage → DEL 本图片级 key → 尝试标记批次完成
    删除触发：
      - 清洗成功后 delete
      - 或 7 天自动过期（若某张只有一边有结果，属异常，过期后不影响批次 COMPLETED 判定
        因为 tryMarkBatchCompleteByTaskUuid 用 keys "minio:flight:img:{taskUuid}*"
        扫描，过期后就扫不到了，自然能顺利标记 COMPLETED，逻辑自洽）。

  tryMarkBatchCompleteByTaskUuid 的完整实现（两个 Service 中分别写会冗余，建议
    抽到 ImageCleanupService 新增 public 方法，两边都调它）：

      public void tryCompleteMinioBatch(String taskUuid, MinioProperties props) {
          Set<String> pending = stringRedisTemplate.keys("minio:flight:img:" + taskUuid + "*");
          if (pending == null || pending.isEmpty()) {
              stringRedisTemplate.opsForValue().set("minio:flight:" + taskUuid, "COMPLETED");
              if (props.isCleanupTempAfter()) {
                  Path tempDir = Paths.get(props.getTempDir(), taskUuid);
                  FileUtil.del(tempDir.toFile()); // hutool cn.hutool.core.io.FileUtil
                  log.info("[MinIO批次] 标记完成并删除临时目录 taskUuid={}", taskUuid);
              }
          }
      }

  注意：此方法若被两个回调线程"几乎同时"进入 -> 可能两次 set COMPLETED 与两次
       FileUtil.del。两者都是幂等，不会有并发问题。

4.8 临时目录、清理、失败重试的衔接
----------------------------------------------------------------------

  目录结构（推荐）：
    下载暂存区：{minio.temp-dir}/{TASK_UUID}/DJI_..._0001_V.jpeg ...  ← 阶段3专用
    长期保留区：{zhimou.image.saveRootDir}/yyyyMMdd/DJI_...jpeg        ← 与阶段2共用

  下载流程：
    MinioClient.getObject(bucket, objectKey) → InputStream → Files.copy 到
      temp-dir/TASK_UUID/filename  ← 批次整体独立，方便处理完成后整个文件夹 rm -rf

  落盘长期保留区（两份 Service 内部仍会做）：
    - ZhimouTaskServiceImpl.createAndReportImageBatch 内部仍按 L2111-L2118 把文件
      从 temp-dir/TASK_UUID/filename copy 到 saveRootDir/yyyyMMdd/filename
    - SelfModelDetectService.detectAndSave 同样 L70-L78 copy 到 saveRootDir/yyyyMMdd/...
      （由于存在同一文件，copy 时使用 REPLACE_EXISTING 与原实现保持一致即可）

  处理完成后删除 temp-dir/TASK_UUID/，避免磁盘积压。
  失败场景：
    - 如果 PROCESSING TTL 30min 过期仍没标记 COMPLETED，MinioPollingService
      下一轮 scan 会"看到该 taskUuid 批次目录，但 Redis 没锁" → 重新 acquireLock。
      由于 temp-dir/TASK_UUID 可能残留，processSingleBatch 开头需要先
      tryMarkBatchComplete 检查后，若仍需处理 → 先删除旧 temp 目录再重新下载
      （或覆盖下载，Files.copy REPLACE_EXISTING，也行）。

  重试：运维接口 POST /api/minio/retry/{taskUuid}
    操作：
      DELETE minio:flight:{taskUuid}
      DELETE minio:flight:img:{taskUuid}*
      MinioPollingService.processSingleBatch(taskUuid)
    （不删 DB，知眸和自有模型若重复调用需要先判断，但更安全做法是：重试只在
      确认之前失败时调用；或者把"重复上报知眸"的风险交给知眸任务本身，因为 imageId
      每次都是从 1 开始，新建知眸任务 taskId 不同，不会串回调。）

    - 还未清洗(clean_status=0) → 自动过滤掉，前端不会展示半成品数据
  这就是"为什么前端零改动就能用"的原因。

  screen-v3 中 dangerSum.vue / alerts.vue 已经适配 image 数据源
  （阶段2已测），无需任何代码调整。

  【阶段3 -> 知眸】
  方法：ZhimouTaskService.createAndReportImageBatch(List<File> images,
                                                     String aircraftSn,          // 阶段3 = detail API drone_sn
                                                     String appId,                // 阶段3 = 配置 defaultAppId
                                                     String applicationPackageId, // 阶段3 = 配置 defaultPkgId
                                                     String imageBaseDir,         // 阶段3 = 配置 saveRootDir
                                                     String customLocalImagePrefix) // 阶段3 = TASK_UUID

  内部：创建知眸 image 任务(taskId) -> 循环 reportImage -> 存 Redis zhimou:img:meta:*
  回调：POST /api/zhimou/callback -> handleCallback(JsonNode root)
    内部：按 (taskId, frameId) 读 meta -> 入库 zhimou_image_detection
                      clean_status=0 -> (阶段3追加) Redis img:zhimou=1 -> 可能触发清洗

  【阶段3 -> 自有模型】
  方法：SelfModelDetectService.detectAndSave(File img,
                                               BigDecimal threshold,     // 0.5 默认
                                               String imageBaseDir,       // 同知眸
                                               String customLocalImageName) // 阶段3 = TASK_UUID/baseWithoutExt
  返回：SelfModelImageDetection
  内部：multipart POST 192.168.2.200:5173/api/v1/detect -> 解析 detections
        -> 入库 self_model_image_detection clean_status=0
        -> (阶段3追加) Redis img:self=1 -> 可能触发清洗

  【图片级自动清洗】
  方法：ImageCleanupService.cleanupSingleImage(String localImageName)
  时机：Redis 图片级 hash 同时含 zhimou=1 和 self=1 的"下一次写入"瞬间
  效果：查两表 -> 距离匹配 -> clean_status 1/2

  【批次级标记完成】
  方法：ImageCleanupService.tryCompleteMinioBatch(String taskUuid, MinioProperties props)
  时机：每次清洗成功后（delete img:key 后）立即尝试
  效果：无 img:taskUuid/* 剩余 -> minio:flight:taskUuid=COMPLETED + 删除 temp 目录

  方法：DjiOpenApiClient.getFlightTaskTrackDetail(defaultProjectUuid, taskUuid)
    -> detail API 返回 flight_pieces[0].drone_sn
  方法：DjiOpenApiClient.getFlightTaskInfo(taskUuid)
    -> folder_info.expected_file_count / uploaded_file_count
  方法：DjiOpenApiClient.getFlightTaskMedia(taskUuid)
    -> list.size() 用于 MinIO 数量二次比对
