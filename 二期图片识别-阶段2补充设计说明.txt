--------------------------------------------------------------------------------
一、问题回顾（根因）
--------------------------------------------------------------------------------

1. 告警页显示原图的根因:
   ZhimouController.buildImageResultVO() 无条件使用 localImagePath（MinIO 原图，
   由 SelfModelDetectService 落盘），而命中记录的 zhimou_app_image（知眸标注图
   相对URL）有值却未被使用。二期回调 handleImageCallback 只存路径不下载图片。

2. 文件混存的根因:
   SelfModelDetectService 落盘原图时 imageBaseDir 复用了一期的 saveRootDir
   (zhimou-images/)，导致一期直播标注图与二期 MinIO 原图混在同一目录。

3. 数据源单选的限制:
   task_switch_config 表 alert_data_source(video/image) 全局单选，控制 admin
   告警管理页与 screen 大屏的警情数据源，同一时间只能看一种告警。

三、数据链路（照片告警全流程）—— 实施后实际纠正版
--------------------------------------------------------------------------------

MinIO 原图下载 (临时目录 zhimou-minio-temp/{taskUuid}/, 批次COMPLETED后删除)
    │
    ├─→ 【纠正】上传知眸前本地暂存 → 二期 zhimou-image-detect/{date}/{taskUuid}/original/
    │       Redis meta.local_image_path 指向二期 original/，**不再写一期目录**
    │
    ├─→ 知眸 reportImage(image_id, device_id, **enhance=1 开启高分辨率小目标增强**)
    │       ↓ 异步回调 POST /api/zhimou/callback
    │   回调格式: data.apps = [ 应用包1(objects:[{x,y,name,color}]), 应用包2, ... ]
    │       ↓ 【关键决策 20260831实飞】一结果一行（不是一图一行、也不是合并成一行）
    │           ├─ for each app 命中 → 插一行记录(zhimou_image_detection)
    │           ├─   每行 app_name/hit_count 单值，不再拼接
    │           ├─   每行 targets_json 只保留当前 app 的 objects（独立可重算）
    │           ├─   每行独立下载该 app 的标注图 (**直接存JPEG, 不转PNG!**)
    │           ├─     文件名 {baseName}_{appId}.jpg（防止两app重名）
    │           ├─   每行写自己的 annotated_local_path（单路径，不再逗号拼接）
    │           └─ 全部插完 → imgKey zhimou=1 → 尝试触发清洗
    │
    ├─→ 自有模型识别 SelfModelDetectService
    │       原图落盘二期 zhimou-image-detect/{date}/{taskUuid}/original/
    │       插入 self_model_image_detection → imgKey self=1 → 尝试触发清洗
    │
    ↓ 两侧到齐 → 逐行独立清洗 ImageCleanupService.cleanupSingleImage()
    │   【关键决策 20260831实飞】不再"合并知眸全部app目标点集"
    │   for each (知眸命中行):
    │       zCenters = 该行自己的 targets_json 解析（不再合并其它行!）
    │       vs 自有模型全部 sCenters (bbox中心点) 一一比距离 <50px
    │       matched = 匹配成功的点数
    │       判定:  zt==0           → clean=1 (正常)
    │          OR (matched>0 AND matched==zt) → clean=2 (误识别)
    │          OR (matched>=5 AND matched*2 >= zt) → clean=2 (误识别, 匹配数≥5 且匹配率≥50%)
    │          ELSE               → clean=1 (正常, 有落单目标需告警)
    │       updateById(该行)   ← 各行 clean_status / clean_remark 独立写!
    │   自有模型行: 知眸任一行 clean=1 → 自有行 clean=1
    │
    ↓
admin 照片告警 /photo-alarm ← GET /image-results/page
    过滤条件: clean_status = 1 (**只显示真实告警, clean=2误识别不显示!**)
              AND hit_count > 0
    图片URL:  annotated_local_path → /image-detect-img/<path>（该app自己的标注图带框）
    【今日发现bug】之前写成 ne(clean_status,0) → 误识别行(clean=2)也全显示, 必须 eq(1)

screen 大屏警情(imgae模式) ← GET /alerts (LIMIT 50)
    过滤条件: 同上 clean_status=1 AND hit_count>0
    图片URL: 同上（带框标注图）
    【轮询决策】飞行中 1 秒刷新; 待机停止（基于 device.modeCode 判定）

四、目录解耦（物理隔离）—— 实施后纠正版
--------------------------------------------------------------------------------

zhimou-images/{yyyyMMdd}/                     ← 一期视频专用【只读不写二期数据】
└── 1788151503385_0c0800d3.png                （直播标注图，存量保留）
                                                一期不再出现 DJI_*.jpeg 照片原图

zhimou-image-detect/                          ← 二期照片专用【所有二期文件都在这里】
└── {yyyyMMdd}/
    └── {taskUuid}/                           ← 一个架次一个文件夹（taskUuid是MinIO fh_sync路径里的uuid）
        ├── original/                         ← MinIO 原图（知眸暂存图 + 自有模型原图都放这里）
        │   └── DJI_20260831124402_0013_V.jpeg
        └── annotated/                        ← 知眸标注图（命中才落盘）
            ├── DJI_20260831124402_0013_V_{appId1}.jpg   （小客车识别标注图, JPEG）
            └── DJI_20260831124402_0013_V_{appId2}.jpg   （人员识别标注图, JPEG）

【纠正】标注图直接存JPEG（知眸原始格式）, 不强制转PNG。
        原设计转PNG导致 5280×3956 的图从10MB胀到 26~58MB（5~6倍膨胀），
        前端 el-image 加载过大 → 页面卡顿转圈。改回 JPEG 直接落盘。

【纠正】上传知眸前的本地暂存图（MinIO下载的照片原图）也放 annotated/ 的父级目录下的
        original/，不再写一期 zhimou-images/，真正做到物理隔离。
        对应 uploadOneImageToZhimou 里 buildImageSavePath 改到二期目录。

静态映射:
  /zhimou-img/**         → zhimou-images/          （一期不变）
  /image-detect-img/**   → zhimou-image-detect/    （二期新增, photoAlarm和screen都用它）

历史数据清理（实施当日已做）:
  TRUNCATE TABLE zhimou_image_detection;
  TRUNCATE TABLE self_model_image_detection;

清洗结果字段说明（一结果一行模型下的语义）:
  zhimou_image_detection.clean_status
    0 = 未清洗/等待自有模型回调（无目标hit=0的历史残留行永远是0, 不影响）
    1 = 正常, 保留告警, admin照片告警 & screen image模式 显示
    2 = 误识别, 【不再显示!】 eq(clean_status,1) 过滤
  clean_remark 格式:
    "误识别:知眸N个目标匹配M个,匹配率%%达阈值"
    "误识别:知眸N个目标全部匹配自有模型"
    "正常:知眸N个目标中M个匹配自有模型"
    "自有模型无有效结果, 判定正常"
  末尾自动加 "[重算]" 标记是用脚本从历史数据回填产生的, 实飞写入不带此标记。

【B. 知眸识别链路】
5. ZhimouOpenApiClient.reportImage()
   URL 追加 &enhance=1，开启高分辨率图片(>2K)小目标增强识别。
   5280×3956 的航拍照片必须开，否则小目标漏检严重。

6. ZhimouTaskServiceImpl.handleImageCallback()【大改 3 次后定版】
   (a) apps 循环: 每 app 命中→插 1 行（一结果一行，不再合并拼接）
   (b) 每行的 targets_json 只保留当前 app 的 objects（独立可重算）
   (c) 每行独立下载该 app 的标注图 JPEG（直接写 byte[]，不转 PNG）
       文件名 {baseName}_{appId}.jpg，防止同图不同 app 覆盖
   (d) annotated_local_path 单路径（不再逗号拼接）
   (e) raw_callback_json 用 Jackson.writeValueAsString(body) 完整存（别用hutool）
   (f) 全部插完 → zhimou=1 → triggerImageCleanupIfReady

【C. 清洗链路】
7. ImageCleanupService.cleanupSingleImage()【大改 2 次后定版】
   (a) 聚合知眸所有命中行，但不再合并 targets_json
   (b) 对每行知眸命中行：
       zCenters = 该行自己的 targets_json 解析
       vs 自有模型全部 bbox 中心点 (50px 半径匹配)
       独立计算 matched 和 clean_status，独立写 clean_remark
       updateById(该行) ← 关键：各行单独写，允许同一图一行clean=2另一行clean=1
   (c) 判定公式：
       全匹配 (matched==zt>0)             → clean=2 误识别
       或 匹配≥5 且 匹配率≥50% (m*2≥zt)   → clean=2 误识别
       其余(落单存在 / 自有无结果 / 匹配不够) → clean=1 正常保留
   (d) 自有模型行：知眸任一行 clean=1 → 自有clean=1；全部clean=2才clean=2
   (e) 匹配计算用整数乘法防浮点误差 (matched*2>=zt 代替 matched/zt>=0.5)

【D. 接口 & 显示口径】
8. ZhimouController：旧 GET /results/page
   删除 alert_data_source 开关判断，固定查一期 zhimou_detection_result。

9. ZhimouController：新增 GET /image-results/page + PUT /image-results/{id}/handle
   page: 固定查二期 zhimou_image_detection；
   ★过滤条件: clean_status = 1 AND hit_count > 0
   【今日bug修复】之前写的 ne(clean_status,0) → clean=2 误识别行也被放出来了！
   handle: 写 work_order_id = System.currentTimeMillis()

    一期手动测试用的本地相对路径（无 taskUuid 斜杠）走 /zhimou-img/；
    标注图 URL 是当前行该 app 自己的带框图。

--------------------------------------------------------------------------------
十、已踩的坑（供后续参考, 绝对不要再犯）
--------------------------------------------------------------------------------

坑1: 一图一行（合并点集）写统一 clean_status → 丢掉了一图内多种app
     结果各自的识别结果, 同图小客车和人员永远一起显/隐 → 错。
     → 最终方案: 一结果一行, 逐行独立 clean。

坑2: 类别语义过滤（人员知眸目标只在自有人员bbox里找匹配, 汽车目标
     只在汽车 bbox 里找）→ 典型的"测试数据抽象过度"。航拍中类别名字符
     串在不同模型/不同版本/不同语言下完全不对齐 (人员/person/人/0/小汽车/
     小客车/汽车/car/vehicle) 匹配结果随机; 而且"自有模型没训人员类"是正
     常业务, 过滤反而导致知眸人员永远在自有里找不到匹配(人为放大距离)。
     → 最终方案: 永远【不用类别过滤】, 行自己的所有目标 vs 自有全部
       bbox 中心点逐一比 50px, 最近的匹配。简单、正确、不依赖字符串。

坑3: ne(clean_status,0) 显示所有"洗过的"行 → clean=2 误识别行也放出来
     → 违反"误识别=剔除不告警"的基本语义。
     → 最终方案: 4 处接口 (ZhimouController×3 + ApiController image) 全
       改 eq(clean_status,1), 只显示真实告警。

坑4: 强制把知眸标注图从 JPEG 转 PNG → 体积胀 5~6 倍。5280×3956 的图单
     张 58MB, 前端 el-image 加载转圈卡死, 页面感知"数据不对"。
     → 最终方案: 直接写知眸原始 byte[] (通常 JPEG), 不做任何格式转换。

坑5: hutool JSONUtil.toJsonStr(Jackson JsonNode) → 序列化为空数组嵌套,
     键名全丢, raw_callback_json 等于白存, 想翻历史原始回调时完全没数
     据可用。
     → 最终方案: 用 Jackson ObjectMapper.writeValueAsString(body), 保持原
       始结构完整。

坑6: 知眸回调标注图 URL 有 ~20 分钟有效期。如果不回调到达时立即落盘,
     想回溯时 404 无法补下载 → 千万不要延后下载。

坑7: 临时脚本 / 调试脚本留在项目根目录 (check_*, monitor_*, backfill_*,
     verify_* 等) 且不加入 git, 造成工作区 40+ 个杂乱文件, 容易混淆
     正式源码。
     → 用完立即删除; 确有长期价值的移到 scripts/ 子目录。

十一、关联背景（本次排查过程要点, 供后续参考）
--------------------------------------------------------------------------------

1. 验证方法: 直接读取 zhimou-images/20260831/1788151503385_0c0800d3.png 确认
   一期直播标注图带橙色检测框+标签（小客车 e9su6b），证明一期链路正常。

2. /results/page 分流逻辑: taskSwitchService.getAlertDataSource()=="image" 时走
   pageImageResults()（查 zhimou_image_detection, 只过滤 clean_status!=0,
   未过滤 hit_count, 且用 localImagePath 拼URL → 显示原图）。

3. 知眸回调字段:
   data.frame.image        = 知眸原始帧图相对URL（/openapi/{taskId}/images/xxx.jpg）
   data.apps[N].image      = 知眸每个app独立的标注图URL
                             （/openapi/{taskId}/messages/{appId}/xxx.jpg）
   data.apps[N].objects[]  = 该 app 的检测目标列表: { x, y, name, color ... }
                             ★只有 x,y 是点坐标, 没有宽高, 不能画矩形框!
                             只能做 50px 中心点匹配。
   apps[].image 在各 app 里各自独立 → 一结果一行的物理基础
   所有路径都是知眸服务器的相对路径, 需拼 openapi.baseUrl 下载。
   ★ 标注图 URL 有效期约 20 分钟 → 回调到达必须立即落盘, 过期无法补。

4. 一期告警状态机制: zhimou_detection_result.work_order_id NULL=未处理,
   非空=已处理; 前端按此显示处理状态并筛选。二期沿用完全相同语义。

5. 自有模型 targets_json 格式 (与知眸格式不同, 不要混淆!)
   [ { class_name: "汽车", confidence: 0.98,
       bbox: { x1, y1, x2, y2 }   ← 矩形左上右下, 中心点((x1+x2)/2,(y1+y2)/2) 参与匹配
     }, ... ]
   没有 name/x/y 结构, 是 class_name/bbox。清洗时统一转为 (cx, cy) 点集 vs
   知眸 (x, y) 点集比距离。

6. 飞行状态判定: 设备的 modeCode
   0=待机, 14=未连接, 3~9=各类飞行模式
   告警轮询判定飞行: modeCode != 0 且 modeCode != 14

7. 清洗的本质（一句话）:
   知眸识别出的"每个目标点"都要在自有模型的同一图中找到 50px 内的对应框，
   找不到 → 说明两系统对该目标没有一致共识，把这行结果保留为真实告警；
   都能找到 或 大量能找到 → 说明是共同场景的共识目标，当作误识别剔除。
